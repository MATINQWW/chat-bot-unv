# نقشهٔ راه: از Vercel تا ۴۰۰۰ کاربر آنلاین داخل اپلیکیشن

همهٔ عددهای این سند **برآورد** هستند. بعد از راه‌اندازی، عددهای واقعی را از پنل مدیر (`/api/admin` ← `stats`) جایگزین کنید.

## ۱. ظرفیت لازم برای ۴۰۰۰ کاربر آنلاین

«آنلاین» یعنی کسی که اپ یا صفحه را باز دارد، نه این‌که همه هم‌زمان پیام بفرستند.

| فرض | مقدار | از کجا اندازه بگیریم |
|---|---|---|
| هر کاربر فعال هر چند وقت یک پیام می‌فرستد | ۱ تا ۲ دقیقه | لاگ‌های اولیه |
| پیام در ثانیه در اوج | ۴۰۰۰ ÷ ۶۰ تا ۱۲۰ ≈ **۳۳ تا ۶۷** | — |
| سهم پیام‌هایی که بدون مدل جواب می‌گیرند (سلام، FAQ، کش) | ۴۰ تا ۶۰٪ | `stats.hit_rate` |
| فراخوانی مدل در ثانیه | ≈ **۱۵ تا ۴۰** | `stats.miss` |
| مدت هر پاسخ جریانی | ۵ تا ۱۰ ثانیه | زمان پاسخ IranCopilot |
| **درخواست هم‌زمان به مدل** = نرخ × مدت | ≈ **۷۵ تا ۴۰۰** | `llm.stats()` |
| توکن ورودی هر فراخوانی | ≈ ۱۱۰۰ تا ۱۳۰۰ (حدود ۳۲۰۰ نویسهٔ فارسی) | `stats.tokens_used ÷ stats.miss` |
| توکن خروجی هر فراخوانی | ≈ ۳۰۰ تا ۸۰۰ (سقف `llm.maxTokens` در `config.js`) | همان |

**نتیجه‌ها:**
1. **مدل:** باید سهمیهٔ RPM/TPM کافی برای حدود ۴۰ درخواست در ثانیه و چند صد درخواست هم‌زمان داشته باشیم. یک سرویس اشتراکی معمولی این را نمی‌دهد. لازم است: سهمیهٔ سازمانی از IranCopilot، به‌علاوهٔ حداقل یک سرویس پشتیبان در `fallback` در `config.js`.
2. **هزینه** با تعداد فراخوانی مدل رابطهٔ مستقیم دارد. هر ۱۰٪ که به `hit_rate` اضافه شود، مستقیماً ۱۰٪ از هزینه کم می‌شود. پس مهم‌ترین کار هفتگی این است که پرسش‌های پرتکرار `topAsked` را به FAQ اضافه کنیم.
3. **هاست:** چند صد اتصال جریانی هم‌زمان روی هاست اشتراکی cPanel **جواب نمی‌دهد** (بخش ۳ را ببینید).

## ۲. مراحل

### مرحلهٔ ۰: الان، روی Vercel ✅
- سرور بدون هیچ سرویس خارجی به‌جز مدل: جست‌وجوی کلمه‌ای + هم‌معنی‌ها (۱۰۰٪ در `npm run eval`)، حافظه داخل instance. (فونت IRANYekan مثل قبل از CDN در مرورگر بارگذاری می‌شود.)
- چند سرویس مدل پشت سر هم با سقف هم‌زمانی و پیام «شلوغ است».
- `server.js` آماده است تا همین کد بدون تغییر روی cPanel یا VPS اجرا شود.
- **محدودیت‌های این مرحله:**
  - rate-limit و حافظهٔ یادگیری در هر instance جدا هستند. یعنی کار می‌کنند، ولی ضعیف.
  - درخواست تماس خاموش است، مگر این‌که `LEAD_WEBHOOK_URL` را بدهید.
- **دو نکتهٔ Vercel:**
  - پلن Hobby فقط برای استفادهٔ شخصی و غیرتجاری است. برای سرویس رسمی دانشگاه، پلن Pro لازم است.
  - دامنه‌های `vercel.app` و اتصال سرورهای خارج به سرویس‌های داخلی ممکن است در ایران مسدود یا ناپایدار شوند. این مرحله برای آزمایش است، نه برای ۴۰۰۰ کاربر.

### مرحلهٔ ۱: آزمایش با تعداد کم کاربر روی cPanel (اگر لازم شد)
- `server.js` با «Setup Node.js App» اجرا می‌شود.
- ✅ **درایور MySQL آماده است** (`lib/kv-mysql.js`): rate-limit مشترک، حافظهٔ یادگیری و درخواست‌های تماس روی MySQL خود هاست؛ فقط `MYSQL_URL` را بگذارید. تست‌شده روی MariaDB 10.11 و در CI روی MySQL 8.
- مناسب برای ده‌ها تا حداکثر چند صد کاربر آنلاین. سقف دقیق را `Entry Processes` هاست تعیین می‌کند.

### مرحلهٔ ۲: ۴۰۰۰ کاربر داخل اپلیکیشن، روی VPS داخلی
- **سرور:** VPS داخلی با ۴ vCPU و ۸ گیگابایت RAM. یک سرور برای کل اپلیکیشن و چت‌بات، یا سرور جدا برای چت‌بات.
- **نرم‌افزار:** Node + `pm2` در حالت cluster (یک پروسه برای هر هسته)، پشت nginx با `proxy_buffering off`.
- **Redis محلی** به‌جای Upstash. لایهٔ `kv.js` همین حالا با دستورهای Redis کار می‌کند و فقط اتصالش عوض می‌شود.
- **اختیاری: جست‌وجوی معنایی محلی** با مدل `multilingual-e5-small` (حدود ۱۲۰ مگابایت، حدود ۳۰۰ مگابایت RAM)، بدون Upstash Vector و بدون اینترنت. فقط اگر `npm run eval` با سؤال‌های واقعی نشان داد جست‌وجوی کلمه‌ای کم می‌آورد.
- **اتصال اپلیکیشن:**
  - اپ موبایل هدر `Origin` نمی‌فرستد. الان `originAllowed` چنین درخواستی را قبول می‌کند و فقط rate-limit جلوی سوءاستفاده را می‌گیرد.
  - برای اپ باید **توکن امضاشده برای هر کاربر** اضافه شود: سرور اپ آن را صادر می‌کند و چت‌بات بررسی می‌کند. rate-limit هم به‌جای IP بر اساس شناسهٔ همان کاربر شود.
- **پایش:** لاگ ساخت‌یافته، هشدار برای خطای ۵۰۳ «شلوغ»، داشبورد `hit_rate` و توکن مصرفی روزانه.

### مرحلهٔ ۳: فقط اگر آمار نشان داد لازم است
- **مدل متن‌باز روی سرور GPU داخلی** (۷ تا ۸ میلیارد پارامتر، با vLLM یا مشابه)، به‌عنوان یکی از سرویس‌های `fallback` در `config.js`.
  - شرط: هزینهٔ ماهانهٔ سرویس‌های اشتراکی از اجارهٔ سرور GPU بیشتر شده باشد.
  - کیفیت پاسخ فارسی‌اش را اول با `eval` و نمونهٔ واقعی بسنجید.

## ۳. چه زمانی باید از cPanel به VPS برویم؟
هر کدام از این‌ها اتفاق بیفتد، وقتش رسیده است:
- خطای **508 Resource Limit Reached** یا 503 از خود هاست (نه پیام «شلوغ» بات). یعنی سقف Entry Processes یا RAM پر شده است.
- بیش از حدود ۲۰ درخواست هم‌زمان به‌طور مداوم.
- زمان اتصال اپلیکیشن به چت‌بات رسیده است. اپ با ۴۰۰۰ کاربر از روز اول VPS می‌خواهد.

دلیل فنی: در هاست اشتراکی هر پاسخ جریانی در تمام مدت تولید پاسخ (۵ تا ۱۰ ثانیه) یک «Entry Process» را اشغال می‌کند، و این سقف معمولاً ده‌ها است، نه صدها.
